## Why CP006 exists

The preceding mission-level ranking package correctly introduced explicit pre-outcome ordering by hypothesis priority, information value and admitted cost. A final adversarial review identified one residual epistemic weakness: if more than one candidate was executable while one or more comparison fields were `UNKNOWN`, deterministic fallback ordering could still emit a candidate as the recommended next action.

Determinism is not scientific justification. The final hardening removes that ambiguity.

## Final behavior

`research/research_os/research_chain.py` now enforces:

1. multiple executable candidates + complete ranking metadata -> rank by explicit hypothesis priority descending, explicit information value descending, then admitted cost ascending;
2. multiple executable candidates + any missing priority / information-value / cost field -> `NO_ACTION`, `executable=false`, `selection_state=RANKING_BLOCKED`;
3. the blocked comparison exposes `MULTI_CANDIDATE_RANKING_INCOMPLETE_FAIL_CLOSED` and `UNKNOWN_RANKING_METADATA_NOT_INFERRED` plus exact `ranking_blockers`;
4. exactly one executable candidate may still be recommended when ranking metadata is incomplete because no cross-candidate dominance is being asserted; the receipt says `SINGLE_EXECUTABLE_NO_COMPARISON`;
5. `UNKNOWN` remains symbolic and is never numerically imputed;
6. outcome/performance-shaped fields remain ignored by the ranking layer;
7. no task is created and no scheduler, Scientific Memory, authority or outcome state is mutated.

The scientific frontier remains independently classified. Therefore a ranking-blocked recommendation can coexist with `ACTIVE_ACTIONABLE`: there may be admissible work, but Mega-A refuses to choose among candidates without sufficient pre-outcome comparison facts.

## New adversarial contract

`test_multiple_executable_candidates_with_unknown_ranking_fail_closed` proves that a cheaper or lexically earlier candidate cannot win merely because another candidate has incomplete ranking metadata.

The test requires:

- `next_action.action == NO_ACTION`;
- no selected `candidate_id`;
- `executable == false`;
- `selection_state == RANKING_BLOCKED`;
- explicit unknown-ranking reason codes;
- frontier remains non-exhausted/actionable where appropriate;
- `scheduler_mutation == false`.

The single-executable UNKNOWN case is separately pinned to avoid over-blocking non-comparative recommendations.
