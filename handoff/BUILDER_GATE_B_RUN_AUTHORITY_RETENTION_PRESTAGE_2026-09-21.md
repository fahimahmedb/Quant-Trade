## 2. F2 — one-run identity, anti-laundering and concurrency

### 2.1 Global run-ID allocation rule

A future run ID SHALL be allocated only by the Blue run-authority registry.

Canonical format:

`GATE_B_RUN_ID = gate-b-<lowercase-rfc4122-uuid-v4>`

Requirements:
1. UUID entropy is generated by a CSPRNG.
2. The candidate ID is checked against the complete authoritative run registry.
3. Reservation is committed by compare-and-swap against the exact prior registry
   head.
4. A collision or stale registry head causes allocation failure and re-read; it
   never causes reuse.
5. An operator may not invent or locally substitute a run ID.

The UUID supplies practical global uniqueness; the authoritative registry makes
uniqueness fail-closed for Quant.

### 2.2 Attempt-number rule

Define the attempt lineage key as:

`(candidate_sha, git_tree, verified_input_tree_digest, target_host_opaque_id)`

For that exact lineage:

`GATE_B_ATTEMPT_NUMBER = 1 + max(prior reserved attempt number)`

If no prior reservation exists, attempt number is `1`.

Attempt numbers are never renumbered, compacted, recycled or decremented. A run
that never reaches mutation still consumes its reserved attempt number once the
reservation is durably committed.

### 2.3 Immutable reservation / consumption ledger

The registry SHALL be append-only. No lifecycle state is represented by editing
an earlier event.

Required event chain per run:

1. `RUN_RESERVED`
2. `ACTIVATION_SEALED`
3. `ACTIVATION_CONSUMED`
4. exactly one terminal event:
   - `RUN_COMPLETED`,
   - `RUN_BLOCKED_TERMINAL`, or
   - `FAILED_TERMINAL`.

Each event SHALL bind at minimum:

- registry schema/version;
- `GATE_B_RUN_ID`;
- attempt number;
- exact candidate SHA/tree/input-tree digest;
- target-host opaque ID;
- previous registry-head digest;
- previous event digest for this run;
- Blue decision/reference;
- activation digest where applicable;
- UTC event time;
- event type;
- operator identity reference where applicable;
- canonical event digest.

A failure to append the next required event leaves the run in
`RECOVERY_REQUIRED`; that state blocks any new activation for the same target
host until Blue issues an explicit recovery disposition. There is no "assume the
old run died" shortcut.

### 2.4 FAILED_TERMINAL semantics

The first mandatory Gate-B FAIL SHALL cause:

```text
GATE_B_RUN_STATUS = FAILED_TERMINAL
ACTIVATION_CONSUMED = TRUE
RUN_REUSABLE = FALSE
```

After that point:
- preserve all red evidence immutably;
- allow only evidence-safe shutdown/collection actions already authorized by the
  activation;
- do not continue the destructive qualification sequence;
- do not overwrite or repair failed artifacts in place;
- do not reuse the activation;
- do not reopen the run ID.

If terminal recording itself fails, classify `RECOVERY_REQUIRED` and block all
new mutating runs until Blue reconciles the registry and host marker.

### 2.5 Retry and evidence-reuse rule

A retry requires ALL of:
- a new globally unique run ID;
- the next attempt number;
- a new immutable reservation;
- a new Blue activation artifact;
- a fresh activation-consumption event.

Default evidence reuse is:

`PRIOR_RUN_EVIDENCE_REUSE_ALLOWED = FALSE`

Blue may explicitly reuse a prior PASS sub-artifact only through a new immutable
`EVIDENCE_REUSE_DISPOSITION` that names:
- prior run ID;
- prior artifact digest;
- prior artifact binding envelope digest;
- property being reused;
- reason reuse remains valid;
- every activation-critical identity that must still match;
- new run ID and new activation digest.

A prior FAIL/UNKNOWN artifact can never be relabeled as PASS. A
`FAILED_TERMINAL` run can never donate an activation or top-level Gate-B
verdict to a later run.

### 2.6 Cross-run relabeling prevention

Every evidence item SHALL be cryptographically bound to the run before its digest
is accepted.

For structured artifacts, the bytes hashed for the artifact digest SHALL contain:
- run ID;
- attempt number;
- activation digest;
- reservation digest;
- target-host opaque ID;
- candidate triple;
- artifact type and ordinal;
- boot ID where relevant;
- creation timestamp.

For raw/binary outputs that cannot embed metadata, create a sidecar binding
envelope containing the raw digest plus all fields above. The manifest binds both
the raw digest and the envelope digest.

A final manifest SHALL reject:
- an artifact whose embedded/envelope run ID differs;
- an artifact whose activation digest differs;
- duplicate logical artifact ordinals;
- an artifact already terminally owned by another run unless an explicit Blue
  reuse disposition exists.

Changing only a top-level JSON run ID can therefore never make old evidence
eligible.

### 2.7 Concurrent mutating-run prevention

Two independent controls are required.

**Blue serialization**

Before sealing an activation, the registry must show no nonterminal run for the
same target host in any of:

`ACTIVATION_SEALED | ACTIVATION_CONSUMED | RUNNING | RECOVERY_REQUIRED`

Reservation/activation publication must be compare-and-swap serialized.

**Target-host serialization**

Before the first mutating operation, a future authority consumer must:
1. verify the sealed activation and reservation;
2. atomically create/verify one persistent active-run marker bound to run ID and
   activation digest;
3. acquire a non-blocking exclusive live lock;
4. durably append `ACTIVATION_CONSUMED`;
5. fsync the control record and containing directory before returning success.

A second consumer, even with the same activation, must fail closed while the
live lock is held. After reboot, the persistent active-run marker survives; only
the same nonterminal run may enter an explicitly authorized resume path.

No such target-host run-authority consumer is presently established by the
reviewed pack. Until implemented and independently tested, this enforcement is a
`MISSING_MECHANISM`.

### 3.6 Expiry, invalidation and revocation

- current time outside `[NOT_BEFORE, EXPIRES)`;
- run reservation no longer current;
- activation already consumed;
- prior terminal FAIL for the run ID;
- candidate SHA/tree/input-tree mismatch;
- hybrid amendment, contract, runbook, schema, materialization procedure,

  synthetic-reservoir binding or mount matrix digest mismatch;
- target-host opaque ID mismatch;
- activation-critical boot ID mismatch;
- evidence-root filesystem/mount identity drift;
- synthetic-reservoir identity drift;
- activation-time preflight is stale under Blue's stated freshness rule;
- authority is superseded in a way Blue marked activation-invalidating;
- revocation epoch changed or activation ID is explicitly revoked;
- Blue explicitly revokes the activation.

The operator must perform the revocation/expiry/current-registry check again
immediately before the first consumer command. A cached earlier "valid" result
is insufficient.

## 4. F6 — persistent restricted evidence retention

### 4.1 Restricted evidence-root requirements

The restricted root must:
- be outside the immutable release;
- be on storage that survives controlled reboot;
- not be tmpfs/volatile runtime storage;
- have a sealed filesystem/mount identity;
- resolve without symlink substitution;
- be writable only by the exact authorized administrative/operator identity;
- deny ordinary users and production service identities unless explicitly
  required;
- use one non-reusable subdirectory per run ID;
- never overwrite a prior run directory.

Recommended layout contract:

```text
<SEALED_EVIDENCE_PARENT>/
  runs/
    <GATE_B_RUN_ID>/
      activation/
      preflight/
      phases/
      raw/
      envelopes/
      manifest/
      public-projection/
```

The exact parent path is a Blue/target-host binding, not invented by this
repository-only prestage.

### 4.2 Reboot persistence

Before destructive work:
- record evidence-root mount/filesystem identity;
- create the run manifest seed only after activation consumption;
- fsync evidence files and containing directories at required seal points.

After every controlled reboot:
- re-resolve the exact evidence-root identity;
- verify the same run directory is retrievable;
- re-hash all manifest entries required for continuation;
- preserve the prior boot evidence;
- fail closed on missing/truncated/moved artifacts.

A changed boot ID is expected after reboot; a changed evidence-root identity is
not silently acceptable.

### 4.3 Journald retention / boot visibility

Activation-time preflight must capture at least:
- effective journald storage mode/configuration and drop-ins;
- journal storage filesystem identity;
- `journalctl --disk-usage`;
- visible boot list;
- current boot ID;
- retention/rotation settings that bound the planned Gate-B/Gate-C evidence
  window.

For a controlled reboot, admissible continuation requires:
- pre-reboot boot ID visible afterward;
- post-reboot boot ID visible;
- required service/lifecycle records retrievable by boot and unit;
- no unexplained journal vacuum/rotation that destroys mandatory evidence.

"journal is currently readable" is not proof of persistence.

### 4.4 Disk / inode headroom

No arbitrary universal PASS threshold is introduced here.

A concrete activation must instead seal a planned evidence budget:
- expected maximum Gate-B restricted-artifact bytes;
- expected journal growth allowance for the campaign;
- inode budget;
- reserve margin chosen by Blue;
- minimum free bytes/inodes required before destructive work.

Activation-time and pre-destructive snapshots must show the budget still fits.
If the budget cannot be justified or headroom is below the sealed requirement:

`GATE_B = BLOCKED`

A stopped service must not be represented as a measured running-process resource
baseline.

### 4.5 Canonical artifact and manifest rules

Every run artifact gets:
- monotonically assigned artifact ordinal;
- canonical artifact type/name;
- creation UTC;
- run ID;
- activation digest;
- candidate triple;
- host opaque ID;
- boot ID where relevant;
- byte length;
- SHA-256 digest;
- classification;
- restricted reference.

Suggested file-name form:

`NNNN_<PHASE>_<ARTIFACT_TYPE>_<UTC>.<ext>`

The final manifest is ordered by artifact ordinal. It contains every raw artifact
and every metadata envelope. Duplicate ordinals or duplicate logical artifact
names are rejected.

The manifest itself is immutable once sealed and receives a SHA-256 digest. A
separate digest sidecar may bind the manifest to avoid a self-digest cycle.

No manifest entry may be deleted because a later phase failed.

### 4.6 Retrievability

A digest without retrievable bytes is insufficient.

Required checks:
1. after writing an artifact, reopen it from the restricted reference and verify
   its digest;
2. before reboot, verify the manifest resolves every mandatory entry;
3. after reboot, repeat retrieval/hash verification for all artifacts required
   to continue;
4. at final seal, resolve every manifest entry again.

Failure to retrieve an allegedly retained artifact is
`MISSING_PROOF / BLOCKED`, not PASS.

### 4.7 Permissions

The activation must bind expected owner UID/GID and mode/ACL policy for:
- evidence parent;
- run directory;
- manifest;
- activation copy;
- raw restricted evidence.

The target-host preflight must compare observed numeric IDs and permissions to
the binding. Human-readable account names alone are insufficient identity.

No production runtime identity may receive write permission merely for
convenience.

### 4.8 Public vs restricted projection

Restricted evidence remains authoritative.

A public projection may contain only Blue-approved non-secret fields such as:
- run ID;
- attempt number;
- candidate triple;
- artifact digests;
- high-level PASS/FAIL/BLOCKED classifications;
- opaque references.

Do not publish:
- requester identity/secrets;
- raw environment files;
- private host identifiers;
- sensitive network configuration;
- raw journals or state inventories containing restricted data.

The public projection must be generated from already sealed restricted evidence
and must bind the restricted manifest digest. It can never replace the
restricted bytes.

### 4.9 Repeatable activation-time preflight

The evidence-retention preflight is a versioned procedure and produces a
restricted snapshot digest.

It must be repeatable:
- once before Blue seals/accepts the concrete activation inputs;
- again immediately before activation consumption;
- again after any activation-critical reboot/environment change when the runbook
  permits continuation.

Each execution records the same field set and command/procedure version.
Differences are classified, not silently normalized.

Required activation-time outputs include:
- evidence-root identity;
- permissions;
- free bytes/inodes;
- journald effective configuration;
- journal disk usage;
- visible boots;
- current boot ID;
- current run-registry/active-marker state;
- retrievability test result.

These observations are `TARGET_HOST_ONLY`; this repository prestage does not
claim them.

## 5. F7 — enforce no-write inspection and prove deployed bytes without index trust

### 5.1 Plain `git status` is not admissible as the no-write proof

The existing runbook's plain:

`git status --porcelain=v1`

must not be treated as proof that the inspection performs no metadata write, and
clean status is not a byte-for-byte deployed-tree proof.

If status is retained only as a secondary diagnostic, use at minimum:

```bash
GIT_OPTIONAL_LOCKS=0 git status --porcelain=v1 --untracked-files=all --ignore-submodules=none
```

and do not use its result as the primary identity proof.

### 5.2 Truly no-write Git inspection

The authoritative inspection path should avoid the mutable index entirely.

Allowed Git reads, with optional locks disabled, include:

```bash
cd "$QUANT_RELEASE"
GIT_OPTIONAL_LOCKS=0 git rev-parse --verify HEAD
GIT_OPTIONAL_LOCKS=0 git rev-parse --verify 'HEAD^{tree}'
GIT_OPTIONAL_LOCKS=0 git ls-tree -r -z --full-tree "$EXPECTED_TREE"
```

These commands read refs/object data and do not require refreshing the worktree
index.

The preflight should additionally verify that no `.git/index.lock` or other
unexpected mutable operation was created by the inspection procedure. A
read-only mount/protection of the release metadata is desirable supporting
evidence, but no-write semantics must not be inferred from a label.

### 5.3 Index-independent deployed-byte verifier

The decisive release-byte proof must compare actual filesystem bytes against the
known expected Git tree without using cached index stat data.

Required verifier algorithm:

1. Anchor expected identity to:
   - exact `EXPECTED_SHA`;
   - exact `EXPECTED_TREE`.
2. Obtain expected tracked entries from `git ls-tree -r -z --full-tree
   "$EXPECTED_TREE"`, not `git ls-files`.
3. Walk the actual release filesystem independently of the Git index.
4. Exclude only explicitly authorized administrative Git metadata and separately
   mounted runtime state paths; do not apply `.gitignore` as an excuse for an
   extra production-code file.
5. For every regular tracked blob:
   - read actual bytes;
   - compute the Git blob object ID from those bytes without `hash-object -w`;
   - compare to the tree entry;
   - compare executable-mode semantics.
6. For every symlink:
   - use the link target bytes, not dereferenced target contents;
   - compare Git blob identity and symlink mode.
7. Reject unsupported gitlinks/submodules unless separately and explicitly bound.
8. Reject any unexpected filesystem entry outside the exact allowed exclusions.
9. Produce a restricted verifier artifact containing:
   - run ID;
   - activation digest;
   - expected/observed SHA and tree;
   - count of expected entries;
   - count of observed entries;
   - mismatches/extras;
   - verifier implementation digest;
   - overall PASS/FAIL.

A verifier that reads the index's "clean" flags is insufficient.

No such exact index-independent verifier artifact is established by the reviewed
pack. Its implementation/digest must be sealed before use:

`DEPLOYED_BYTE_VERIFIER = MISSING_MECHANISM`

## 7. Activation blockers that remain after this prestage

This prestage intentionally does not convert missing mechanisms or host
observations into proof.

1. F1 repaired evidence schema must be delivered, exact-head checked,
   independently rechecked and Blue-promoted.
2. Lane A/F4 must deliver an exact transition plan that Blue can approve and
   digest-bind. The current Lane-A handoff is an interim checkpoint only.
3. F5's synthetic-reservoir separation/sanitization mechanism must exist before
   F3's synthetic binding can be nonblank.
4. The run-authority registry/atomic consumer/revocation mechanism described
   above must exist and have an immutable implementation digest.
5. The index-independent deployed-byte verifier must exist and have an immutable
   implementation digest.
6. F6 target-host evidence-root/journald/headroom/retrievability observations
   must be performed at activation time.
7. No concurrent mutating Gate-B run may exist.

None of these is waived by this handoff.
