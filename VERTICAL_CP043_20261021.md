## Concrete descent and failures

The dataclasses were frozen, but their annotated tuple fields accepted caller
lists and retained those references. After construction, clearing or appending
to an issuer/security/name/ticker/listing lineage list changed the book's future
resolution proof. A resolution could lose evidence or include an evidence hash
that had never been validated. CorporateActionEvent also retained mutable legs
and evidence lists: a valid MERGER could lose its required legs or acquire a
forbidden SPIN leg after admission. These are changes inside the same modules,
not loss of identity at an external handoff.

The first repair captured these sequences as tuples. It fixed the 33 initial
cases (20 previously failing), but deeper falsification then found 14 more
failures: tuple(dict) silently discarded metadata values, and set inputs admitted
unqualified ordering. These nonsequence containers were not valid instances of
the declared list/tuple contract. Both weaknesses remain grouped in this CP;
there is no new checkpoint number for the additional failure found while descending.

Root causes: shallow retention of mutable sequence inputs; container coercion
without validating its declared shape. Two repair items, not 34 independent roots.

## Narrow repair

The five identity evidence constructors validate a captured tuple and store that
same tuple in their frozen field. Corporate-action events capture legs and
lineage before their existing semantic checks. Admission explicitly accepts
list/tuple sequence inputs and rejects mappings/sets/other containers instead of
silently dropping values/order. Existing evidence-hash, PIT and action-kind checks
are retained. The dataclass fields and canonical JSON array representation stay
the same; Python wire reconstruction now restores the declared tuple identity.

Compatibility: callers supplying dictionaries, sets or generators where the
contract declares a tuple must provide an explicit valid sequence. No source
metadata is silently interpreted as evidence or quantity. Existing valid list and
tuple inputs, evidence order, event semantics and lookup clocks remain compatible.
Nested action-leg dictionaries still require the existing explicit dataclass
reconstruction; no new JSON parser or vendor identity repository is built.
