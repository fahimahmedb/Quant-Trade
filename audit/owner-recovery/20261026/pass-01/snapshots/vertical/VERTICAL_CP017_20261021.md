# Vertical CP017 — Scientific hash ledger snapshot and publication integrity

Module: existing Research OS scientific memory (`scientific_store.py`).
Capability: append, verify and publish its existing hash-chained scientific
snapshot/trial ledger. North Star scientific memory and experiment infrastructure
require preserving historical truth and immutable scientific identity. Starting
depth: D1, existing ordinary chain and payload-tamper tests.

Four repair items, with related manifestations grouped:

1. Caller payloads and append receipts aliased committed entries. Mutating a
   returned trial record or receipt silently changed already-hashed history.
2. Malformed kinds/payloads were admitted; malformed entry shapes could raise
   from verification, extra unhashed fields and boolean sequence values passed.
   Publication/extension did not require a valid existing chain.
3. JSONL publication directly truncated the destination. It had no staging,
   fsync or atomic replacement, and could publish a tampered chain.
4. Append selected sequence/previous hash without an instance lock, allowing
   competing threads to fork the same chain. A deterministic paused-hash test
   reproduces this; the stress control alone is not the concurrency proof.

Narrow repair: freeze payloads as strict JSON objects with string keys, reject
nonfinite/unserializable content, detach returned receipts; serialize append,
verification and publication under one instance RLock. Verification requires the
exact envelope fields and integer sequence and returns false for tested malformed
states. Invalid chains cannot be extended or published. Unique same-directory
staging, file fsync, replacement and directory fsync publish complete snapshots.
Global canonical_json/hash behavior for other Research OS artifacts is unchanged.

Adversaries: input/receipt/trial-export nested mutations; malformed kinds, nested
keys and values; malformed envelope/null/extra/missing/bool sequence/nonfinite
payload; corruption followed by append/publication; replacement failure; file and
directory fsync failure; retry and byte-identical repeat publication; reconstructed
chain verification; deterministic competing append and 100-append thread control.

Before repair: **20 failed / 2 passed** across 22 new cases. After repair:
**44 passed / 1 skipped** across those cases and the existing multi-engine and
persistent-final-shape suites. Before/after transcripts are preserved at
`research/vertical_depth/20261021/CP017_{before,after}.txt`.

Attained depth: **D3**, scoped to same-instance append serialization, detached
snapshot identity and atomic publication/retry with injected local failures.
A post-replacement fsync error propagates: callers must treat it as an ambiguous
ACK; rereading sees a complete new document and identical retry is safe. No false
claim of physical crash survival or authenticated provenance is made.

Remaining unproven: direct public entries mutation/races, caller concurrent input
mutation, adversarial Python subclasses, independent ledger instances publishing
the same destination (last replacement wins), authenticated chain anchoring,
rollback/truncation attacks that recompute valid hashes, semantic scope conflicts,
large-ledger performance (append checks the existing chain), actual process/power
loss and distributed filesystems. This is snapshot export, not a new durable
append/recovery database or idempotent ingestion API.

Horizontal findings: none. Longitudinal findings: none.
Owner authority bypass found here: FALSE. Only synthetic local fixtures run.
